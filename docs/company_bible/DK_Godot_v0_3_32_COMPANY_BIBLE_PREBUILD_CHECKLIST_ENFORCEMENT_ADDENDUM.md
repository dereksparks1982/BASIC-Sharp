# DK Godot v0.3.32 Company Bible Prebuild Checklist Enforcement Addendum

**Date:** 2026-07-09  
**Status:** Mandatory  
**Scope:** Every Demon Killer build, patch, hotfix, repair, scaffold, tool update, validation package, and equivalent implementation request

## First-action rule

When Dick says **build**, **patch**, **hotfix**, or gives equivalent implementation authorisation, the first action must be to read the current Company Bible and all applicable active addenda.

This happens before:

- announcing a version or build title;
- defining or narrowing scope;
- proposing an implementation route;
- editing any project file;
- creating a backup;
- generating documentation;
- validating or packaging;
- relying on remembered rules.

Memory is not a substitute for the current project records. There is no guessing where build compliance is concerned.

## Required prebuild order

1. Read the active Company Bible and applicable addenda.
2. Read the current master handoff, canonical project roadmap, failure log, migration plan, controls, relevant system records, any outside analysis that produced an accepted or pending decision, and the active system contract for the work being changed.
3. For DKPlayer work, read `docs/player/DKPLAYER_BEHAVIOURAL_INVENTORY_AND_REPLACEMENT_CONTRACT_v0_3_51.md` before touching replacement code.
4. For lore or Tapestry work, read `docs/tapestry/DK_TAPESTRY_CANON_FOUNDATION_v0_3_51.md`; keep reader canon separate from production notes.
3. Inspect the actual uploaded project files.
4. Confirm protected-file, backup, version, documentation, validation, and package requirements.
5. Only then begin the authorised build.

## Documentation remains mandatory every time

Every numbered deliverable must carry its complete documentation set, including the applicable:

- visible version updates;
- changelog;
- patch notes;
- session log;
- changed-files record;
- handoff;
- canonical project roadmap update;
- active system-contract update when the build advances a roadmap lane;
- Tapestry canon update when lore decisions are made;
- outside-analysis decision record when an external report was received or used;
- system or migration documentation;
- validation record;
- manifest and package hash record;
- Company Bible addendum when a mandatory workflow rule changes or is reinforced.

No build is too small to document. No spoken authorisation waives the documentation rules unless Dick explicitly changes the Company Bible itself.

## v0.3.32 application

The first attempted response to the v0.3.32 build request began announcing work before the Bible had been read. Work was stopped. This addendum records the correction so the same failure cannot become normal practice.
